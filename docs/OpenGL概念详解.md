## 0. 先建立一个心智模型

### 0.1 一个关键事实：GPU 看不见你的内存

你的 `float NDC_vertices[]` 在 **CPU 内存（RAM）** 里。

但显卡有它自己的内存（**显存 / VRAM**），而且**GPU 只能读显存，读不到 CPU 内存**。

所以任何要参与渲染的数据，第一件事都是**搬到显存里**。这就是 VBO 存在的理由。

### 0.2 GPU 是一台只会做三件事的机器

抛开所有细节，GPU 干的活只有三件：

| # | 干什么 | 谁定义的 | 跑几次 |
|---|---|---|---|
| 1 | **读顶点数据** | 你（通过 VAO 告诉他怎么读） | —— |
| 2 | **对每个顶点跑一次"你给的函数"** | 你（顶点着色器） | 顶点数（三角形 = 3 次） |
| 3 | **对每个像素跑一次"你给的函数"** | 你（片元着色器） | 三角形覆盖的像素数 |

**中间还有一步"光栅化"**（把三角形切成像素），那是硬件固定功能，**你写不了代码，也不需要**——这一步正是你软件管线里手写的那部分（扫描线填充、重心坐标插值）。

**所以在 OpenGL 里，你写的代码 = 两个函数 + 一堆"喂数据"的调用。** 没有别的了。

### 0.3 三个"抽屉柜"

整个 OpenGL 的数据模型可以概括成三个柜子：

```
┌─────────────────────────────────────────────────────────────┐
│  VBO —— 一个"字节数组"                                       │
│  装的是原始顶点数据，GPU 不知道里面是什么格式                 │
│  就是一块显存，等价于你的 std::vector<float>                  │
├─────────────────────────────────────────────────────────────┤
│  VAO —— 一张"说明书"                                         │
│  说明"上面那个字节数组，前 3 个 float 是位置，             │
│        每个顶点隔 12 字节，从第 0 字节开始"                   │
│  它自己不存数据，只存"怎么解释数据"                           │
├─────────────────────────────────────────────────────────────┤
│  Program —— 一个"可执行程序"                                 │
│  由顶点着色器 + 片元着色器链接而成，GPU 真正跑的东西          │
└─────────────────────────────────────────────────────────────┘
```

**记住这个三层结构，后面所有问题都能挂上去。**

## 1. 一个顶点从 CPU 到屏幕的完整旅程

```
【CPU 内存】
  float NDC_vertices[9] = { 0.0, 0.5, 0.0,  -0.5,-0.5,0.0,  0.5,-0.5,0.0 }
        │
        │  ① glBufferData(GL_ARRAY_BUFFER, 36, NDC_vertices, GL_STATIC_DRAW)
        │     —— 把 36 字节从 CPU 内存复制到显存
        ▼
【显存：VBO】一块 36 字节的裸字节数组（GPU 不知道格式）
        │
        │  ② glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, 12, 0)
        │     —— 告诉 VAO："位置属性 = 每 12 字节取前 3 个 float"
        ▼
【显存：VAO】说明书（记录 ① 用的哪个 VBO + ② 的格式）
        │
        │  ③ glDrawArrays(GL_TRIANGLES, 0, 3)
        │     —— "按这份说明书，读 3 个顶点，按三角形画"
        ▼
┌───────────────────────────────────────────────────────┐
│ GPU 固定功能：顶点取指（Vertex Fetch）                 │
│ 按第 ② 步的记录，从 VBO 里切出 3 个 vec3               │
└───────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────┐
│ 顶点着色器 × 3                                        │
│ 输入：aPos（vec3）     输出：gl_Position（vec4）       │
│ 你写的那 3 行 GLSL 就干这个                            │
└───────────────────────────────────────────────────────┘
        │
        │  gl_Position 的 w 分量在这里被用来做"透视除法"
        ▼
┌───────────────────────────────────────────────────────┐
│ 图元装配 + 裁剪 + 光栅化（全部硬件）                   │
│ 把 3 个 clip space 坐标 → 屏幕上的像素集合             │
│ 顺便对属性做插值（重心坐标）                            │
└───────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────┐
│ 片元着色器 ×（被覆盖的像素数）                          │
│ 输入：插值后的值      输出：FragColor（vec4）           │
│ 你写的那 3 行 GLSL 就干这个                            │
└───────────────────────────────────────────────────────┘
        │
        │  深度测试、混合（硬件）
        ▼
【帧缓冲】一块显存里的图像
        │
        │  glfwSwapBuffers(window)
        ▼
【屏幕】
```

### 这个旅程里，"你"和"硬件"的分工

| 环节 | 谁做 | 我的软件管线里对应什么 |
|---|---|---|
| 数据上传到显存 | 我调 API | 无（我的数组本来就在内存里） |
| 顶点取指（按格式切数据） | 硬件（读 VAO） | 我手写的 `for` 循环取 `vertices[i]` |
| 顶点变换 | **我写着色器** | 我手写的矩阵乘法 |
| 透视除法 | 硬件 | 我手写的 `w` 除法 |
| 光栅化（三角形→像素） | 硬件 | 我手写的扫描线填充 |
| 属性插值 | 硬件 | 我手写的 `LiniarInterpolation` |
| 深度测试 | 硬件（可配置） | 我手写的 `DepthBuff` 比较 |
| 决定像素颜色 | **我写着色器** | 我手写的 `DrawPixel` |

**结论**：我少写的那 4 件事（取指、透视除法、光栅化、插值），正是 OpenGL 帮我做的。**这就是"少写十分之九代码"的来源。**

## 2. 着色器（Shader）是什么

### 2.1 一句话

**着色器 = 一段用 GLSL 写的、由 GPU 执行的程序。**

它的特殊性在于：**同一段代码会被 GPU 并行地跑成千上万次**——每个顶点一次，或每个像素一次。你写"一个顶点怎么处理"，GPU 负责对全部顶点同时做。

### 2.2 为什么不能直接用 C++ 写

| 原因 | 说明 |
|---|---|
| **要跨硬件** | 不同显卡的指令集不同。GLSL 是标准语言，驱动负责翻译成该卡的机器码 |
| **要能大规模并行** | GPU 有几千个核心同时跑同一段代码（SIMD/SIMT）。C++ 的写法（递归、动态分配、虚函数）没法这样跑 |
| **要在显存里跑** | GPU 不能访问 CPU 内存，也不能调用 `new`/`malloc`、不能读写文件 |

所以 GLSL 是**受限的、为并行设计的语言**：没有指针、没有堆分配、没有递归（现代版本有宽松限制）、只有有限的库函数。

### 2.3 我的猜想：Python 的 `exec` 类比

我写的原始问题是：

> Python 可以做到把一串字符串的引号去掉以后把结果当作程序代码运行。这里也有类似的机制吗？

**这个类比直觉很准，但要修正一个关键点。**

**相同的地方**：都是"把字符串当代码"。
**不同的地方**：

| | Python `exec(src)` | OpenGL 着色器 |
|---|---|---|
| 谁执行 | **CPU**，你的进程 | **GPU**，显卡 |
| 何时编译 | 运行时，每次调用 | 运行时，**但只编译一次**（`glCompileShader` 之后结果被保存） |
| 执行几次 | 1 次 | **顶点数 / 像素数**次，且**并��** |
| 能做什么 | 任何事（文件、网络、内存） | 只能做"算一个值"，无副作用（除了输出） |
| 上下文 | 可以访问全局变量 | 只能访问"你传进去的"数据 |

**最重要的差别**：`exec` 是"解释执行一次"，着色器是"**编译成 GPU 机器码，然后并行执行成千上万次**"。所以 `glCompileShader` 这一步是**真的编译**（生成机器码），不是解释。

### 2.4 `#version 460 core` 是干什么的

```
#version 460 core
```

**三个部分**：

| 部分 | 含义 |
|---|---|
| `#version` | 预处理指令，告诉编译器"这是版本声明" |
| `460` | GLSL 版本号，`460` = **GLSL 4.60**。前两位是主版本，后两位是次版本 |
| `core` | 使用 **Core Profile** 语义（对应你 `glfwWindowHint(GLFW_OPENGL_PROFILE, GLFW_OPENGL_CORE_PROFILE)`） |

**三条硬规则**：

1. **必须是源码的第一行**。前面不能有空行、不能有注释、**不能有 BOM**（这就是为什么把着色器写成字符串很安全——字符串里没有 BOM）
2. **版本号不能超过上下文支持的版本**。你的上下文是 4.6，所以最高能写 `460`
3. **`core` 和 `compatibility` 二选一**。写 `core` 意味着用 Core Profile 的语义（`gl_FragColor` 之类老东西不可用）

**如果写错会怎样**：整个着色器编译失败，日志里会说 `ERROR: 0:1: '' : version '460' is not supported`。

**为什么必须声明**：GLSL 没有"默认版本"的安全假设。不同版本的语法差异很大（比如 1.10 用 `attribute`/`varying`，3.30+ 用 `in`/`out`），编译器必须先知道按哪套规则解析。

### 2.5 `layout(location = 0) in vec3 aPos;` 逐词拆解

这行是我问题里说的"看起来不像 C++ 代码"的那行。拆开看：

```
layout(location = 0)  in      vec3   aPos   ;
└──────┬──────────┘   └┬┘     └─┬─┘   └─┬─┘  └┬┘
       │               │        │       │     │
   【属性位置】     【输入】  【类型】  【名字】 【语句结束】
```

| 部分 | 含义 | 为什么需要 |
|---|---|---|
| `layout(location = 0)` | 这个属性绑定到**位置 0** | **必须和 `glVertexAttribPointer` 的第一个参数一致**，这是 CPU 和 GPU 之间的"约定编号" |
| `in` | 声明为"输入变量" | 表示数据从**上一步**流进来。在顶点着色器里，`in` = 从 VBO 来的属性 |
| `vec3` | 3 个 float 的向量 | 位置是 x,y,z 三个分量 |
| `aPos` | 变量名（随便取） | 在 `main()` 里用它 |

**关键理解：`layout(location = 0)` 是一个"插槽编号"。**

```
CPU 侧：glVertexAttribPointer(0, 3, ...)   ← "我要配置 0 号插槽"
GPU 侧：layout(location = 0) in vec3 aPos  ← "0 号插槽的数据叫 aPos"

                    ┌──── 编号必须对上 ────┐
```

**如果编号对不上会怎样**：GPU 会去读一个没配置的插槽，拿到未定义数据 → 三角形消失或乱画，**且不报错**。

> **补充**：`location` 也可以不写。不写的话由驱动自动分配编号，你之后用 `glGetAttribLocation(program, "aPos")` 去问。但**显式写死更简单也更安全**，所以教程都用 `layout(location=...)`。

### 2.6 `gl_Position` 是什么，为什么必须写

```glsl
void main() {
    gl_Position = vec4(aPos, 1.0);
}
```

**`gl_Position` 是顶点着色器唯一必须写的东西**：它代表"这个顶点在**裁剪空间（clip space）**中的位置"。

| 要点 | 说明 |
|---|---|
| 类型必须是 `vec4` | 因为裁剪空间是 4 维齐次坐标 |
| 这是一个**内置变量** | 不用声明，OpenGL 预定义好的 |
| 不写它 = 未定义行为 | 常见表现是画不出东西 |
| **不需要做透视除法** | 你给 `w`，硬件帮你除 |

**为什么是 4 维**：第 4 个分量 `w` 就是齐次坐标的关键。透视投影矩阵会把"离相机多远"编码进 `w`，硬件随后做 `x/w, y/w, z/w` —— **这就是透视效果的全部来源**。

你软件管线里手写的这段：

```cpp
// 你的透视除法（伪代码）
x_ndc = x_clip / w;
y_ndc = y_clip / w;
z_ndc = z_clip / w;
```

**在 GPU 上就是"你在着色器里给了 w，硬件自动除"**。你一行代码都不用写。

`vec4(aPos, 1.0)` 里的 `1.0` 就是 `w`。**w = 1.0 表示"这个点在无穷远平面上，不做透视变形"** —— 所以三角形直接显示成平面图形，没有透视收缩。这也是为什么三角形阶段不需要矩阵。

### 2.7 片元着色器

```glsl
out vec4 FragColor;

void main() {
    FragColor = vec4(1.0, 0.5, 0.2, 1.0);
}
```

| 部分 | 含义 |
|---|---|
| `out vec4 FragColor` | 声明一个**输出变量**，它会写到颜色缓冲 |
| 变量名随便取 | `FragColor` 是习惯叫法，不是关键字 |
| `vec4(r, g, b, a)` | 颜色，四个分量都是 **0.0 ~ 1.0** |

**为什么 Core Profile 必须自己声明 `out`**：老版本（GLSL 1.10）有一个预定义的 `gl_FragColor`，直接赋值就行。**Core Profile 把它移除了**，强制你声明自己的输出变量——好处是支持多渲染目标（MRT，一次输出多张图）。

**为什么"片元"不叫"像素"**：一个"片元（fragment）"是"一个像素位置上的候选颜色"。它还要经过深度测试、混合，才最终变成像素。**名字的差别提示了"它不是最终结果"。**

### 2.8 编译是什么过程？编译成什么？怎么运行？

这是我最想问清楚的问题。完整链条如下：

```
你写的 GLSL 字符串（44 个字符左右）
        │
        │  ① glCreateShader(GL_VERTEX_SHADER)
        │     创建一个空的"着色器对象"，得到一个 ID
        ▼
【着色器对象：空壳】
        │
        │  ② glShaderSource(vs, 1, &src, nullptr)
        │     把源码字符串交给它（只是存起来，还没动）
        ▼
【着色器对象：有源码了】
        │
        │  ③ glCompileShader(vs)
        │     ★ 真正编译：驱动把它翻译成 GPU 机器码 ★
        ▼
【着色器对象：含编译后的 GPU 代码】
        │
        │  ④ glGetShaderiv(vs, GL_COMPILE_STATUS, &ok)   查成功与否
        │     glGetShaderInfoLog(...)                    失败时取日志
        ▼
        │  ⑤ glCreateProgram() + glAttachShader ×2 + glLinkProgram(prog)
        │     把"顶点 + 片元"两个编译产物链接成一个完整可执行程序
        ▼
【Program：GPU 可执行程序】
        │
        │  ⑥ glUseProgram(prog)   （每帧）
        │     告诉 GPU"接下来用这套程序"
        ▼
        │  ⑦ glDrawArrays(...)
        │     GPU 真正开始执行
        ▼
   屏幕上的三角形
```

**"编译"具体做了什么**（第 ③ 步）：

| 阶段 | 干什么 |
|---|---|
| 词法分析 | 把字符流切成 token（`void`、`main`、`{` …） |
| 语法分析 | 按 GLSL 文法构建语法树 |
| 语义检查 | 类型检查、变量是否声明、`gl_Position` 是否被赋值 |
| **生成 GPU 机器码** | 针对**当前这块显卡**的指令集生成代码 |

**关键认识：编译结果是和显卡绑定的。** 同一段 GLSL 在 NVIDIA 和 Intel 上编译出的机器码不同。**这也是为什么着色器不能像 DLL 一样分发预编译版本**（除非用 SPIR-V）。

**"怎么运行"**：不是你的 CPU 调用它。`glDrawArrays` 之后，GPU 的调度器把那个 Program 派发给上千个核心，每个核心拿一个顶点（或像素）的数据跑同一段机器码。

### 2.9 链接完就能删着色器？编译结果是怎么被持有的？

我写的原始问题：

> 链接完了就可以删程序 -> 编译结果是怎么被持有的？

**答案：靠"引用计数"。**

`glDeleteShader(shader)` 的语义**不是立即销毁**，而是：

> **标记为待删除。如果真的被删了，那要等到它不再依附于任何 program 为止。**

所以在你的代码里：

```cpp
glLinkProgram(prog);        // prog 已经可以独立运行了
glDeleteShader(vertice_vs); // 标记待删；但它还挂在 prog 上，所以此刻并未真正释放
glDeleteShader(plate_fs);
```

**这不会泄漏**，因为：

1. `glLinkProgram` 已经把两个着色器的编译产物**合并进了 program 的可执行代码**
2. 着色器对象此刻只是"外壳"，标记后它会在 program 被删除时一并释放
3. 你之后用 `glUseProgram(prog)` 用的是 program，不需要着色器对象

**一句话**：`glDeleteShader` = "我不用它了，你可以在我松开最后一根线时收走"。

**类比**：像 `std::shared_ptr` 的 `reset()`——对象还活着，只是少了一个持有者。

## 3. VAO 与 VBO

### 3.1 VBO（Vertex Buffer Object）：显存里的一块字节数组

**是什么**：一块**显存**，装原始字节。**GPU 完全不知道里面是什么格式**——它只是 36 个字节。

**为什么需要**：因为 GPU 读不到你的 CPU 内存（见 0.1）。

**对应关系**：

| CPU 侧 | GPU 侧 |
|---|---|
| `float arr[9]` | VBO（36 字节显存） |
| `std::vector<float>` | VBO |
| `memcpy` 到显存 | `glBufferData` |

**VBO 本身是"哑"的**：它不知道"前 12 字节是一个顶点的位置"。**这需要 VAO 来说明。**

### 3.2 VAO（Vertex Array Object）：一张说明书

**这是最容易误解的一个。** 让我先破除三个常见误解：

| ❌ 误解 | ✅ 事实 |
|---|---|
| VAO 存顶点数据 | **不存**。数据在 VBO 里 |
| VAO 是 VBO 的另一个名字 | **完全不同的东西** |
| VAO 可有可无 | **Core Profile 里必须有**，没有就画不出东西 |

**VAO 到底存什么**（确切清单）：

| 存的内容 | 对应 API |
|---|---|
| 每个顶点属性用**哪个 VBO** | `glBindBuffer` 的当前绑定 |
| 每个属性的**分量数、类型、是否归一化** | `glVertexAttribPointer` 的参数 ②③④ |
| 每个属性的 **stride 和 offset** | `glVertexAttribPointer` 的参数 ⑤⑥ |
| 每个属性**是否启用** | `glEnableVertexAttribArray` |
| （还有 EBO 的绑定） | `glBindBuffer(GL_ELEMENT_ARRAY_BUFFER, ...)` |

**所以 VAO = "顶点数据的一份读取说明书"。**

**类比**（用你熟悉的东西）：

> VBO 是一本**二进制数据表**，VAO 是**读取这张表的格式说明**（"每 12 字节为一组，前 3 个 4 字节是位置"）。
>
> 你换一本数据表（换 VBO）但读取格式不变，可以复用说明书；你换格式（加颜色），就要改说明书。

### 3.3 为什么 `glGen*` 只给"名字"？

我写的原始问题：

> API 文档里面说这个函数是拿来申请几个存名字的地址的，为什么要这么干？

**因为 OpenGL 的对象模型是"句柄制（handle-based）"。**

```cpp
GLuint vao = 0;
glGenVertexArrays(1, &vao);   // ← 此时 vao 得到一个非零整数，比如 1
```

| 问题 | 答案 |
|---|---|
| `glGen*` 干了什么 | **仅**向 OpenGL 注册"我要用这个编号"，返回一个整数 ID |
| 它分配显存了吗 | **没有** |
| 那什么时候分配 | 在 `glBindBuffer` + `glBufferData` 时（对 VBO）；在 `glVertexAttribPointer` 时（对 VAO 的内容） |
| 为什么返回值不是直接返回而要传出参数 | 因为要支持"一次生成 N 个"，所以传数组 + 数量 |

**参数表**：

```cpp
void glGenVertexArrays(GLsizei n, GLuint* arrays);
void glGenBuffers      (GLsizei n, GLuint* buffers);
```
- 参数 ① `n`：生成几个
- 参数 ② `arrays`：**输出参数**，把生成的 ID 写进这个数组（这就是为什么传 `&vao`）
- 返回值：`void`

**为什么要这种两步设计**（先给名字，后绑定时才分配）：

1. **延迟分配**：可以先要到 ID，稍后再真正绑定并填充数据
2. **统一的对象模型**：所有 OpenGL 对象（VBO / VAO / texture / framebuffer / shader / program）都是"先 gen 拿 ID，再 bind 使用"
3. **ID 是 0 表示无效**：所以你的 `GLuint vao = 0;` 初始化是对的——如果 `glGen` 失败，它还是 0，可以检测

**一个小事实**：你控制台输出的 `vao = 1`、`vbo = 1` —— 都是 1，是因为这两类对象**各自独立编号**，都是从 1 开始。不是"同一个对象"。

### 3.4 为什么一个叫 VAO 一个叫 VBO？为什么不用同一个？

我写的原始问题：

> `glGenBuffers(1, &vbo);` 为什么这里又变成 VBO 了？

因为它们是**两类不同的对象**，用不同的 `glGen` 生成：

| | VBO | VAO |
|---|---|---|
| 生成函数 | `glGenBuffers` | `glGenVertexArrays` |
| 全称 | Vertex **Buffer** Object | Vertex **Array** Object |
| 本质 | 一块**字节内存** | 一份**状态记录** |
| 类比 | 硬盘上的数据文件 | 读取该文件的解析规则 |
| 数量关系 | 一个 VAO 可引用多个 VBO | 一个 VBO 可被多个 VAO 引用 |

**`glGenBuffers` 的"Buffers"是复数泛称**：它不只生成 VBO，还能生成 EBO（索引缓冲）、UBO（uniform 缓冲）等。**具体是什么类型的 buffer，由后面 `glBindBuffer` 的第一个参数决定**（`GL_ARRAY_BUFFER` = 顶点缓冲）。

### 3.5 为什么要绑两次？

我写的原始问题：

> `glBindBuffer(GL_ARRAY_BUFFER, vbo);` 为什么要这样干？

因为 **`glBindVertexArray` 和 `glBindBuffer` 绑的是两种完全不同的东西**：

```cpp
glBindVertexArray(vao);                    // ① 绑定"说明书" → 之后的属性设置都写进它
glBindBuffer(GL_ARRAY_BUFFER, vbo);        // ② 绑定"数据"   → 之后 glBufferData 写进它
glBufferData(GL_ARRAY_BUFFER, ...);        //    往 ② 绑定的 VBO 里写数据
glVertexAttribPointer(0, 3, ...);          //    往 ① 绑定的 VAO 里记"怎么读 ② 的 VBO"
```

**关键：`glVertexAttribPointer` 同时用到"当前绑定的 VAO"和"当前绑定的 VBO"。**

```
       glVertexAttribPointer(0, 3, ...)
                 │
        ┌────────┴────────┐
        │                 │
   当前绑定的 VAO     当前绑定的 VBO
   （写进说明书）      （记录"读这个"）
```

**如果只绑了 VBO、没绑 VAO 会怎样？**

> Core Profile 下，`glVertexAttribPointer` **会失败但没有明显报错**（或写入一个不存在的默认 VAO），最终 `glDrawArrays` 画不出东西。这是最经典的静默失败。

**顺序为什么不能反**：

```cpp
glBindBuffer(GL_ARRAY_BUFFER, vbo);   // 先绑 VBO
glBufferData(...);                    // 上传数据（需要 VBO 已绑）
glBindVertexArray(vao);               // 再绑 VAO
glVertexAttribPointer(...);           // 记录格式（需要 VAO + VBO 都在）
```

其实**"先绑 VAO 还是先绑 VBO"不影响结果**，只要在 `glVertexAttribPointer` 那一刻两者都绑着就行。你的顺序是先 VAO 再 VBO，完全正确。

### 3.6 完整调用链图解

```
┌─ 一次性初始化 ─────────────────────────────────────────────┐
│                                                             │
│  glGenVertexArrays(1, &vao)   →  vao = 1   （只是拿到 ID）  │

│                                                             │
│  glBindVertexArray(vao)       →  "现在开始写 1 号说明书"    │

│         "属性 0 = 从当前 VBO 的第 0 字节开始，              │
```

## 4. `glVertexAttribPointer`：六个参数逐项拆解

我写的原始问题：

> 我想知道这个函数参数都是啥，返回值是啥，深入探究这个函数主要执行了什么功能，为什么这些参数是必要的，运作原理是什么。

### 4.1 它到底做了什么

**一句话：把"一串裸字节"翻译成"一串属性向量"的规则，写进当前绑定的 VAO。**

```
VBO 内容（36 字节，GPU 眼中就是一串字节）：
┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
│ 0.0f │ 0.5f │ 0.0f │-0.5f │-0.5f │ 0.0f │ 0.5f │-0.5f │ 0.0f │
└──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
  ↑0     ↑4     ↑8     ↑12    ↑16    ↑20    ↑24    ↑28    ↑32    （字节偏移）

glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, 12, 0) 之后，
GPU 就知道：
  顶点 0 的 aPos = 从偏移 0  读 3 个 float = (0.0, 0.5, 0.0)
  顶点 1 的 aPos = 从偏移 12 读 3 个 float = (-0.5, -0.5, 0.0)
  顶点 2 的 aPos = 从偏移 24 读 3 个 float = (0.5, -0.5, 0.0)
```

### 4.2 六个参数

```cpp
void glVertexAttribPointer(GLuint index, GLint size, GLenum type,
                           GLboolean normalized, GLsizei stride,
                           const void* pointer);
```

| # | 参数 | 你填的 | 含义 | 为什么必要 |
|---|---|---|---|---|
| ① | `index` | `0` | **属性插槽编号** | 决定"这份格式给哪个 `layout(location=N)`" |
| ② | `size` | `3` | 这个属性占**几个分量** | 位置是 xyz = 3；颜色也是 3；UV 是 2 |
| ③ | `type` | `GL_FLOAT` | 每个分量的**数据类型** | 决定"把这 4 个字节解释成浮点还是整数" |
| ④ | `normalized` | `GL_FALSE` | 是否把整数**归一化**到 [0,1] 或 [-1,1] | 若用 `GL_UNSIGNED_BYTE` 存颜色，就要设 `GL_TRUE` |
| ⑤ | `stride` | `12` | **相邻两个顶点之间隔多少字节** | GPU 靠它找"下一个顶点从哪开始" |
| ⑥ | `pointer` | `(void*)0` | 这个属性在顶点内的**字节偏移** | GPU 靠它找"这个属性从顶点的第几字节开始" |

**返回值**：`void`。**而且它不会报错告诉你填错了**——参数错了只会表现为"画不出来"或"画得乱七八糟"。这是它最坑的地方。

### 4.3 参数 ⑤⑥ 的完整图解（最关键）

```
一个顶点占 12 字节（3 个 float × 4 字节）

       ┌─────────── stride = 12 字节 ───────────┐
       │                                        │
       ▼                                        ▼
┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
│ 0.0f │ 0.5f │ 0.0f │-0.5f │-0.5f │ 0.0f │ 0.5f │-0.5f │ 0.0f │
└──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
 ↑                    ↑                    ↑
 │  offset = 0        │  offset = 0        │  offset = 0
 │  （顶点 0 起点）    │  （顶点 1 起点）    │  （顶点 2 起点）
```

**顶点 N 的属性地址 = VBO 起点 + offset + N × stride**

```
顶点 1 的位置 = 0 + 0 + 1×12 = 12  ✓（和上图一致）
顶点 2 的位置 = 0 + 0 + 2×12 = 24  ✓
```

### 4.4 加颜色之后会变成什么样

下一步（阶段 3.5）你会给每个顶点加 3 个 float 的颜色，那时：

```
每个顶点 24 字节

     ┌──────────────── stride = 24 ────────────────┐
     ▼                                             ▼
┌──────┬──────┬──────┬──────┬──────┬──────┐
│ 位置x│ 位置y│ 位置z│ 颜色r│ 颜色g│ 颜色b│  ...下一个顶点...
└──────┴──────┴──────┴──────┴──────┴──────┘
 ↑                    ↑
 offset = 0          offset = 12
 （位置属性）         （颜色属性）

glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, 24, (void*)0);              // 位置
glVertexAttribPointer(1, 3, GL_FLOAT, GL_FALSE, 24, (void*)(3*sizeof(float))); // 颜色
```

**注意 `stride` 从 12 变成 24**——因为一个顶点变大了。**这是加属性时最容易忘的一处。**

**另一种组织方式**（不交错，两个独立 VBO）：

```
VBO_A：[位置0][位置1][位置2]      stride=12, offset=0
VBO_B：[颜色0][颜色1][颜色2]      stride=12, offset=0
```
这叫"分离缓冲"，性能上各有取舍。**初学用交错（interleaved）就好**。

### 4.5 `void*` 是什么东西？为什么要强转？

我写的原始问题：

> `void*` 是什么东西？

**`void*` 是"无类型指针"**——只知道是一个地址，不知道指向什么类型。

**为什么这里用它**：因为参数 ⑥ 需要一个"字节偏移"，但 C 的类型系统里没有"偏移量"这个类型（`int` 看起来像"值"，`size_t` 也行但 API 设计者选了指针）。所以 OpenGL 沿用了"把偏移量伪装成指针"的写法：

```cpp
(void*)0                      // 偏移 0 字节
(void*)(3 * sizeof(float))    // 偏移 12 字节
```

**记住：这个指针不会被解引用（不会真的去读那块内存）。它只是一个装偏移量的容器。**

**这属于 OpenGL 的历史遗留设计**，确实很怪。现代 API（Vulkan、WebGPU）都改成了 `uint64_t offset` 或 `GLuintptr`。

**为什么必须强转**：直接写 `3 * sizeof(float)`（是 `size_t`）会编译报错，因为不能隐式转成 `const void*`。所以 `(void*)` 是为了通过类型检查，不是为了运行。

### 4.6 `glEnableVertexAttribArray` 为什么必需？

我写的原始问题：

> `glEnableVertexAttribArray(0)` 参数都是啥，返回值是啥，主要执行了什么功能，为什么这些参数是必要的，运作原理是什么。

```cpp
void glEnableVertexAttribArray(GLuint index);
```

| 项 | 内容 |
|---|---|
| 参数 | `index` = 属性插槽编号（和 `glVertexAttribPointer` 的第一个参数一致） |
| 返回值 | `void` |
| 作用 | **打开这个插槽的"阀门"** |

**为什么必须单独一个调用**：因为每个属性插槽有**两个独立的状态**：

```
┌─────────────────────────────────────────┐
│  属性插槽 0                              │
│  ┌─────────────────┐  ┌───────────────┐ │
│  │ 格式（怎么读）   │  │ 开关（是否启用）│ │
│  │ glVertexAttrib  │  │ glEnable...   │ │
│  │ Pointer 设置    │  │ / glDisable   │ │
│  └─────────────────┘  └───────────────┘ │
└─────────────────────────────────────────┘
```

**默认是关闭的**。不开的话，GPU 会用一个常数值代替这个属性（默认 (0,0,0,1)），**你的顶点位置全变成 0** → 三角形缩成一个点 → 什么都看不见。

**为什么要拆成两个函数**：因为存在"配置了但暂时不用"的合法场景。比如：

- 一个 VAO 配了位置 + 颜色 + UV 三条属性
- 画"纯色物体"时只启用位置和颜色，**关掉 UV**（省带宽）
- 画"贴图物体"时再打开 UV

**这叫"一个 VAO 多种用法"**，是性能优化手段。所以"配置"和"启用"必须是两个独立的开关。

## 5. `glDrawArrays`：最后一步

```cpp
void glDrawArrays(GLenum mode, GLint first, GLsizei count);
```

| 参数 | 你填的 | 含义 |
|---|---|---|
| `mode` | `GL_TRIANGLES` | 图元类型（三角形 / 线 / 点） |
| `first` | `0` | 从第几个顶点开始读 |
| `count` | `3` | **读几个顶点**（不是画几个三角形） |

**`count` 是最容易错的**：你想画 1 个三角形，但 `count` 要填 **3**（顶点数）。填 1 只会送 1 个顶点，凑不成三角形 → 什么都不显示。

**`GL_TRIANGLES` 的语义**：每 3 个顶点组成 1 个三角形。所以：

| count | 画出几个三角形 |
|---|---|
| 3 | 1 |
| 6 | 2 |
| 36 | 12（立方体） |

**`glDrawArrays` 之前必须准备好三件事**：

1. `glUseProgram(prog)` —— 有程序可用
2. `glBindVertexArray(vao)` —— 有说明书可用
3. （VAO 里已经记好了 VBO）—— 有数据可用

**缺任何一个都画不出东西，而且都不报错。**

## 6. NDC 的定义：我的猜想与 OpenGL 的实际

我写的原始问题：

> OpenGL 的 NDC 空间定义，xy 两个轴都应该是 [-1,1]。-> 我需要确认一下 NDC 的定义以验证我的猜想。这里的 NDC 定义和我的 NDC 定义不一样。

### 6.1 猜想正确的部分

**x、y ∈ [-1, 1]** ✅ 完全正确。

```
        y = +1
          ▲
          │
x=-1 ◄────┼────► x=+1
          │
          ▼
        y = -1
```

**(0, 0) 在屏幕中心**，这就是为什么你的三角形 (0, 0.5) 顶点出现在中间偏上。

### 6.2 容易搞错的部分：z

| | NDC 的 z 范围 |
|---|---|
| **OpenGL** | **[-1, +1]** |
| **DirectX** | [0, 1] |
| **我的软件管线**（`Perspective.h`） | [0, 1] ← 跟的是 DirectX 传统 |

**两个不同的"z"，别混**：

| 概念 | 范围 | 在哪一步 |
|---|---|---|
| **NDC 空间的 z** | GL 里是 [-1, 1] | 透视除法之后 |
| **深度缓冲里的值** | 永远是 [0, 1] | 视口变换之后 |

**视口变换会做这个映射**：`z_depth = (z_ndc + 1) / 2`。

所以 NDC 的 -1 → 深度 0（最近），NDC 的 +1 → 深度 1（最远）。

### 6.3 这对你的下一步有实际影响

如果你把 `GeneratePerspectiveMatrix` 生成的矩阵（z 映射到 [0,1]）**直接**用到 OpenGL 上：

```
你的矩阵产出 z_ndc ∈ [0, 1]
                       ↓ 视口变换 (z+1)/2
深度缓冲里的值 ∈ [0.5, 1.0]
                       ↓
★ 只用到了深度范围的后一半 ★
```

**后果**：能正常渲染，**但深度精度损失一半**（远处的 z-fighting 会更容易出现）。

**这是"能用但不最优"的典型**。两种处理：

| 做法 | 结果 |
|---|---|
| 先按现值走（[0,1]） | 能跑，视觉上没问题；等出现 z-fighting 再改 |
| 改矩阵让 z 映射到 [-1,1] | 用到完整深度精度，但和你软件管线的约定不一致了 |

**建议**：**先按现值走**，等你真的看到 z-fighting（远处物体表面出现条纹闪烁）再去优化。**过早优化会掩盖真正的 bug。**

### 6.4 关于"迁就 OpenGL 的标准"

我在代码注释里已经决定：

> 我的技术选择是迁就已有定义和代码风格。

**这个决定是对的，而且理由比"方便"更硬**：

> **x 轴方向必须迁就 GL。** 我的 NDC 是 `+X 朝左`，GL 是 `+X 朝右`。如果坚持我的约定，所有后续对接（模型导入、光照公式、第三方工具、RenderDoc 抓帧）都要来回翻转一次——**每次翻转都是一个 bug 的机会**。

**但 z 的 [0,1] vs [-1,1] 可以先接受**，因为它只影响精度不影响正确性。

```cpp
// ───────────── 每帧 ─────────────
while (...) {
    glViewport(...);                                     // 换算：NDC → 像素
    glClear(...);                                        // 清屏
    glUseProgram(prog);                                  // 选程序
    glBindVertexArray(vao);                              // 选说明书
    glDrawArrays(GL_TRIANGLES, 0, 3);                    // ★ GPU 开跑
    glfwSwapBuffers(window);                             // 呈现
}
```

**三个 ★ 就是整个渲染的核心动作**：数据上传、着色器编译、发起绘制。

## 8. 为什么 OpenGL 让人困惑：隐式状态机

> 这一节是全篇的收束。前面所有"为什么要这样写"的疑惑，根源都在这里。

### 8.1 拆两个词

**状态机**：一个系统有一组"状态变量"，它的行为**取决于当前状态**，而操作会**修改状态**。

**隐式**：状态变量**不作为参数出现**。你调函数时，看不出它到底在操作哪个对象——它读的是"当前绑定的那个"。

合起来：

> **隐式状态机 = 状态藏在全局，函数靠"当前状态"决定行为，而不是靠你传进来的参数。**

### 8.2 我其实一直在用它：EasyX

我的主仓库 `Fern3DGameEngine` 里，`Window::Clear()` 是这么写的：

```cpp
void Clear() {
    cleardevice();       // 注意：没有颜色参数！
}
```

`cleardevice()` 凭什么知道要清成什么颜色？**因为它读的是"当前背景色"这个隐藏状态**（由 `setbkcolor()` 设置）。

同理 `setcolor(red); line(...)` —— `line()` 也没有颜色参数。

**这就是隐式状态机。我在写软件渲染器时一直在用，只是没给它起名字。**

### 8.3 对比：显式 vs 隐式

同样一件事——画一个网格：

**显式风格（Vulkan / Direct3D 12）**

```cpp
cmd.beginRenderPass(pass);          // 明确：用哪个 pass
cmd.bindPipeline(pipeline);         // 明确：哪个管线
cmd.bindVertexBuffers(buffer, 0);   // 明确：哪个缓冲
cmd.draw(36, 1, 0, 0);
```

**隐式风格（OpenGL）**

```cpp
glUseProgram(prog);        // ← 设置"当前程序"这个隐藏状态
glBindVertexArray(vao);    // ← 设置"当前 VAO"这个隐藏状态
glDrawArrays(GL_TRIANGLES, 0, 36);
//    ↑ 三个参数只说：画什么图元、从第几个顶点开始、画几个顶点
```

**`glDrawArrays` 没有说：用哪个着色器程序？读哪个顶点数组？写进哪个帧缓冲？**

—— 这三件事全靠"当前状态"。

### 8.4 它会有三种咬法

#### 咬法一：副作用取决于看不见的状态

`glVertexAttribPointer` 是最好的例子：

```cpp
glBindVertexArray(vaoA);
glVertexAttribPointer(0, 3, ...);   // ← 写进 vaoA

glBindVertexArray(vaoB);
glVertexAttribPointer(0, 3, ...);   // ← 完全相同的调用，写进 vaoB
```

**同一个函数、同样的参数，结果是写到不同的对象里**——区别只在"调用时绑的是谁"。

**代价是：读代码时必须自己在脑子里维护一份"当前绑定表"。**

#### 咬法二：状态会泄漏到后面的代码

```cpp
glBindVertexArray(vaoA);
drawObjectA();

glBindVertexArray(vaoB);     // 中途切了
drawObjectB();

drawObjectA();               // ❌ 忘了重新绑！画的是 vaoB
```

**没有报错，只是画错了。** 这就是为什么我养成了"每帧画之前都显式 `glBindVertexArray`"的习惯——**不要假设它还绑着**。

#### 咬法三：失败是静默的

OpenGL 的错误处理也是隐式的：

```cpp
glDrawArrays(...);           // 参数全错也不会抛异常
GLenum e = glGetError();     // 得主动去问"刚才出错了吗"
```

对比 C++ 的异常与断言——**OpenGL 默认什么都不说**。所以关键步骤后必须主动 `glGetError()`。

### 8.5 我已经被它咬过的两次

| 经历 | 本质 |
|---|---|
| 忘绑 VAO 就 `glDrawArrays` → **黑屏无报错** | 读到了"当前 VAO = 无" |
| `glGetString` 写在 `gladLoadGLLoader` 之前 → **`0xc0000005` 崩溃** | 不完全是状态问题，但同属"隐式前置条件"：函数指针还没被填上 |

> 顺便，第二次崩溃的同一类错误后来又犯了一次：`glEnable(GL_DEPTH_TEST)` 写在 `gladLoadGLLoader` 之前，同样 `0xc0000005`。
> **教训固化成规则**：所有 `gl*` 调用必须写在 `gladLoadGLLoader` 之后。

### 8.6 设计者的补偿：VAO 本身就是"状态打包"

这一点很妙——**VAO 的存在，正是为了对抗隐式状态机的复杂度**：

```
没有 VAO（老式 GL）：
  每次画之前都要重新设置：绑 VBO、开属性、设格式……
  → 6 次状态设置 × 每个物体

有 VAO：
  绑定 1 个 VAO = 一次性恢复全部顶点相关状态
  → 1 次状态设置 × 每个物体
```

> **所以 VAO 不是"多了一层抽象"，而是把一堆散落的隐式状态打包成一个可整体切换的单元。**
> 这是对隐式状态机的**局部修正**——不是消灭它，而是把它收敛到可控的粒度。

### 8.7 真实引擎怎么对付它

| 手段 | 说明 |
|---|---|
| **状态缓存** | 记住"当前 program 是谁"，避免重复设置：<br>`if (curProg != prog) { glUseProgram(prog); curProg = prog; }` |
| **状态排序** | 把使用同一个 program / 同一个 VAO 的物体排在一起画，减少切换次数 |
| **渲染器层封装** | 自己写一层 `Renderer`，对外提供显式接口（`DrawMesh(mesh, material, transform)`），内部管理隐式状态 |

**这就是为什么图形引擎里总有一个"渲染器层"**——它的核心职责之一，就是**把 OpenGL 的隐式状态机包成显式接口**，让上层业务代码不必记住"当前绑的是谁"。

### 8.8 一句话总结

> **隐式状态机 = 函数的行为不取决于参数，而取决于"你之前做了什么"。**
>
> **优点**：省参数，且给了驱动优化的空间（状态完整时它可以合并/批处理操作）。
> **代价**：你必须自己维护一份心里的状态表，而且**错了不报错**。

### 8.9 面试可以这样答

> "OpenGL 是隐式状态机：`glDrawArrays` 的参数里没有'用哪个程序'、'读哪个 VAO'，它读的是当前绑定。这个设计省了参数、也给了驱动优化空间，但要求你严格维护绑定状态，而且配置错了往往不报错、只黑屏。
>
> 所以我在自己的工程里养成了两个习惯：画之前显式重绑 VAO、关键步骤后查 `glGetError`。而 VAO 本身其实就是对这套散装状态的一次打包——把'顶点相关的全部状态'收成一个可以整体切换的单元。
>
> 对比来看，Vulkan 把这个状态全部显式化了（pipeline、command buffer），代价是代码量爆炸，但**可预测性更强、多线程友好**。"

### 8.10 一个附带的认识

"隐式状态机"和多态一样，是**我已经在用、但不自知的概念**。

知道名字之后，两个变化：

1. **能预测坑在哪**——凡是"设置状态 → 执行动作"分离的 API（EasyX、OpenGL、GDI、很多音频/网络库），都会有状态泄漏问题
2. **能读懂设计意图**——OpenGL 的 API 看起来"步骤繁多"，不是设计者偷懒，而是**状态机 + 静默失败 + 跨驱动可移植**这三个约束共同作用的结果

## 9. 一页速查

### 对象与用途

| 对象 | 生成 | 绑定 | 作用 | 一句话 |
|---|---|---|---|---|
| VBO | `glGenBuffers` | `glBindBuffer(GL_ARRAY_BUFFER, …)` | 显存里的字节数组 | "数据放在哪" |
| VAO | `glGenVertexArrays` | `glBindVertexArray` | 读取格式的说明书 | "数据怎么读" |
| Shader | `glCreateShader` | ——（用 attach） | 单个编译单元 | "一段 GPU 函数" |
| Program | `glCreateProgram` | `glUseProgram` | 链接后的可执行体 | "真正跑的东西" |

### 两个"插槽编号"必须一致

```
glVertexAttribPointer(0, ...)         ← CPU 侧
layout(location = 0) in vec3 aPos;    ← GPU 侧
                      └─ 必须相等 ─┘
```

### 三个静默失败（不报错，只是黑屏）

| 忘做什么 | 后果 |
|---|---|
| 忘 `glBindVertexArray` 就画 | 说明书不存在 → 画不出 |
| 忘 `glEnableVertexAttribArray` | 属性全为 0 → 缩成一点 |
| 着色器编译失败但不查 | 用空程序画 → 画不出 |

### 我的软件管线 vs GPU

| 我手写的 | GPU 里由谁做 |
|---|---|
| `for` 循环取顶点 | 顶点取指（读 VAO） |
| 矩阵乘法 | 顶点着色器（我写 GLSL） |
| `w` 除法 | 硬件 |
| 扫描线填充三角形 | 硬件光栅化 |
| `LiniarInterpolation` 属性插值 | 硬件 |
| `DepthBuff` + 深度比较 | 硬件（`glEnable(GL_DEPTH_TEST)`） |
| `putpixel` 上色 | 片元着色器（我写 GLSL） |
| `windowMatrix` 视口变换 | `glViewport` |

**这就是为什么 GPU 版本代码量少十倍：中间那 6 行全是硬件做的。**
